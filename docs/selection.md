## 1. 공통 요구 사항

- Unity 6.3 LTS, C# 9, 새 Input System. 수업 프로젝트에 넣어 바로 돌릴 수 있어야 한다.
- 패턴 이름보다 **수강생이 실제로 겪는 증상**에서 시작한다. 효과 끄기(나쁜 예)가 그 증상을 재현한다.
- 게임 규칙은 순수 C# 코어에 둔다 (dotnet 대조와 '테스트하기 쉬운 구조' 수업을 함께).
- **교안 연계**: 표본마다 교안의 어느 장을 잇는지, 교안의 '상황' 코드가 실행 중에 어떻게 깨지는지를 카드에 적는다. 교안의 '상황' 은 대부분 유지보수 비용(분기가 늘어난다)이라, 표본은 그 분기가 **실제로 어긋나는 순간**을 찾아 무대에 보인다.
- 교안의 비게임 예제(결제, 커피, 쿠폰, 파일 트리, 신호등)는 같은 구조의 게임 상황으로 바꾼다.
- 원리의 출처는 Robert Nystrom 의 *Game Programming Patterns* (웹판 공개)와 Unity 전자책 *Level up your code with design patterns and SOLID* 를 우선 링크한다. 둘 다 없는 패턴(데코레이터, 전략)은 GoF *Design Patterns* (1994) 를 이름으로 적는다. 글과 코드는 새로 쓴다.

## 2. 그룹별 카드

### A 행동

**`state-player-actions` 상태 패턴: 플레이어 행동** ★

- 수업에서 왜 필요한가: 수강생 플레이어 코드의 가장 흔한 형태가 `isJumping`, `isAttacking` bool 덩어리다. 조작을 하나 더할 때마다 버그가 곱으로 는다.
- 무대와 시나리오: 걷다가 공격 중 점프, 공중에서 공격, 걷는 중 피격 (자동 데모). 공격 중 피격, 공중 공격 허용.
- 효과 끄기: bool 플래그 넷과 if 문. 공격 자세로 점프, 맞아도 공격이 이어짐, 경직 중 걷기와 점프.
- 확인된 대표작: 없음 (범용 기법). 출처: Nystrom 'State', Unity 전자책.
- 겹치는 표본: 없음. 이후 계층 상태 기계, 적 AI 상태 기계 표본의 바탕.
- 교안과의 차이: 교안은 슬라임 AI 를 enum + switch 로 짠 코드를 나쁜 예로 쓴다. 그 상황은 묶음 3 `state-drone-ai` 가 맡는다.

**`strategy-turret-targeting` 전략 패턴: 포탑 조준 방식** ★ — 묶음 2

- ID `strategy-turret-targeting`, 그룹 A, 순서 2, 난이도 1.
- 한 줄: 포탑은 조준 방식 객체에게 대상을 묻기만 하고, 방식은 실행 중에 갈아 끼운다.
- 수업에서 왜 필요한가: 교안 Strategy.md 의 '타워 조준' 그대로다. 조준 방식을 문자열이나 enum 의 if 사슬로 고르면, 같은 사슬이 조준 표시(레이저)와 발사에 따로 생기고, 새 방식을 한 곳에만 더해 둘이 엇갈린다. 교안이 가장 강조한 'State 와 헷갈리기' (전이가 있으면 상태, 바깥이 골라 끼우면 전략)를 상태 표본과 나란히 보일 수 있다. 교안의 브리지(무기 × 인챈트)는 같은 '합성으로 갈아 끼우기' 라 이 표본 글에 녹인다 ("포탑 종류 × 조준 방식을 상속으로 곱하지 않는다").
- 무대와 시나리오: 정비 기지(오른쪽) 앞 포탑 하나. 잔해 드론 4~5대가 정해진 간격, 속도, HP 로 왼쪽에서 다가온다 (난수 없음). 포탑은 `fireInterval` 마다 쏜다. 조준 레이저는 `arrow`, 명중은 `ring`, 드론 HP 는 `bar`. 입력: `nearest` 가까운 것, `strongest` 체력 많은 것, `first` 기지에 가장 가까운 것, `weakest` 체력 적은 것 (새로 더한 방식). 자동 데모(6초 안팎): 가까운 것 → 약한 것 (엇갈림) → 선두 → 강한 것. 시나리오 2: 쏘는 중 방식을 바꾸면 다음 발사부터 대상이 바뀐다. 시나리오 3: `range` 를 줄여 사거리 밖 드론은 어떤 방식이든 고르지 않는다. 조절 값: `range`, `fireInterval`, `damage`.
- 효과 끄기: 포탑 하나가 `UpdateAim()` 과 `Fire()` 에 각자 `if (mode == ...)` 사슬을 가진 흔한 코드. '약한 것부터' 를 `Fire()` 에만 더해서, 그 방식일 때 레이저는 기본값(가까운 것)을 가리키고 총알은 다른 드론에 맞는다. ✖ `조준 엇갈림`. 미니 월드에서 레이저 끝과 명중 링이 다른 드론에 있다.
- `mistakes` 후보: State 와 헷갈려 전략이 스스로 다음 전략을 고름, 전략 객체에 포탑별 값(마지막 대상)을 넣고 두 포탑이 같이 써서 섞임 (교안 '전략에 상태를 잔뜩 넣기'), 매 프레임 `new` 로 전략을 만듦, 파괴된 드론을 대상으로 붙들고 있음.
- 확인된 대표작: 없음 (범용 기법). 출처: 교안 `3. Behavioral/02. Strategy/Strategy.md`, GoF 'Strategy', Unity 전자책 (Strategy 장 수록 여부 미확인, 6절).
- 겹치는 표본: `state-player-actions` (상태와 전략의 차이). 같은 무대 상황을 묶음 3 `facade-hit-resolution`, `factory-drone-spawner` 가 이어 쓸 수 있다 (정비 기지 방어).

**`state-drone-ai` 상태 패턴: 잔해 드론 AI** ★★ — 묶음 3

- ID `state-drone-ai`, 그룹 A, 순서 3, 난이도 2.
- 한 줄: 적 AI 의 순찰·추격·공격·파괴를 상태 객체로 나누고, 들어갈 때 바꾼 것을 나올 때 되돌린다.
- 수업에서 왜 필요한가: 교안 State.md 의 주 예제(슬라임 AI 를 enum + 거대 switch 로)와 같은 모양이다. 수강생이 가장 많이 짜는 적 AI 가 이 모양이고, 교안이 강조한 "진입·이탈 1회 처리" (공격에 들어가면 멈추고, 나오면 다시 움직임)가 switch 에서 가장 자주 빠진다. 플레이어 입력으로 전이하는 `state-player-actions` 와 달리 **거리와 체력으로 스스로 전이**하는 적을 보인다.
- 무대와 시나리오: 땅 위 잔해 드론 하나와 하린. 하린이 다가가면(입력) 드론이 감지 거리 안에서 추격, 공격 거리 안에서 멈추고 충전 뒤 사격, 하린이 물러나면 다시 추격·순찰, 피해가 쌓이면 파괴. 자동 데모: 다가감 → 공격 → 물러남(추격으로 돌아감) → 다시 다가감 → 파괴.
- 효과 끄기: `enum DroneState` + `Update` 의 switch. 공격에 들어갈 때 `speed = 0` 을 하지만 나올 때 되돌리는 곳이 없어 ✖ `이동 멈춤` (추격 상태인데 제자리). 진입 처리를 case 안에서 매 프레임 해 충전이 계속 처음부터 시작되거나, 파괴 뒤에도 사격 case 가 도는 것 중 하나를 둘째 ✖ 로.
- 교안 연계: `ChangeState` 한 곳에서만 Exit → Enter, 같은 상태 클래스를 다른 드론이 재사용, 상태 상속으로 확장(글).
- 출처: Nystrom 'State', Unity 전자책 (상태 장).
- 겹치는 표본: `state-player-actions` (같은 패턴, 입력 대 거리 전이, bool 대 enum 나쁜 예).

**`hierarchical-state-enemy` 상태 패턴: 계층 상태 기계** ★★★ — 묶음 4

- ID `hierarchical-state-enemy`, 그룹 A, 순서 4, 난이도 3.
- 한 줄: 여러 상태에 공통인 규칙(EMP, 경계등)을 부모 상태 한 곳에 두고, 자식 상태는 자기 일만 한다.
- 수업에서 왜 필요한가: `state-drone-ai` 처럼 상태를 클래스로 나눠도 상태가 늘면 공통 규칙("EMP 맞으면 기절", "전투 중엔 경계등")을 상태마다 복사한다. 나중에 더한 상태가 복사를 빠뜨리고, 전투 안에서 추격 → 공격으로 옮길 때 추격의 Exit 가 경계등을 끈다. 부모 상태가 공통 규칙을 맡고, 전이는 공통 조상까지만 나갔다 들어온다 (Nystrom 'State' 의 계층 상태 기계 절).
- 무대와 시나리오: `state-drone-ai` 와 같은 땅, 드론, 하린. 상태 트리 Active{순찰, 수색(나중에 더함), 전투{추격, 공격}}, 기절. 입력: 다가감, 물러남, EMP. 자동 데모: 다가감 (순찰 → 추격 → 공격) → 물러남 (공격 → 추격 → 수색) → 수색 중 EMP.
- 효과 끄기: `state-drone-ai` 의 평평한 상태 클래스 구조. 수색 상태가 EMP 규칙을 복사하지 않아 ✖ `EMP 무시`, 추격 Exit 가 끈 경계등을 공격 Enter 가 켜지 않아 ✖ `경계등 꺼짐`.
- 출처: Nystrom 'State' (계층 상태 기계 절).
- 겹치는 표본: `state-drone-ai` (앞 편. 이 표본의 나쁜 예가 그 구조), `state-player-actions`.

**`update-method-drone-list` 업데이트 메서드: 드론 목록 한 프레임** ★★ — 묶음 5

- ID `update-method-drone-list`, 그룹 A, 순서 5, 난이도 2.
- 한 줄: 매니저가 드론 목록을 돌며 하나씩 업데이트하되, 도는 중에 생기고 사라지는 드론은 루프 밖에서 정리한다.
- 수업에서 왜 필요한가: 적이 많아지면 수강생은 매니저 하나가 목록을 도는 구조로 옮긴다. 그 순간 "도는 중에 지우면 다음 적을 건너뜀", "도는 중에 더한 적이 태어난 프레임에 바로 움직임", `foreach` 에서 지우면 `InvalidOperationException` 이 나온다. Unity 의 `Update` 도 같은 패턴이라는 것과 함께.
- 무대와 시나리오: 잔해 드론 여럿이 나란히 기지 쪽으로 움직인다. 기지에 닿거나 피해로 파괴되면 목록에서 빠지고, 분열 드론은 업데이트 중에 둘로 나뉜다. 드론마다 업데이트 횟수를 보인다.
- 효과 끄기: `for (i = 0; i < drones.Count; i++) drones[i].Update(dt)` 안에서 드론이 자기를 `Remove` 하고 새 드론을 `Add` 하는 흔한 코드. ✖ `업데이트 건너뜀` (지워진 드론 다음 드론이 그 프레임에 안 움직임), ✖ `태어난 프레임에 움직임`.
- 출처: Nystrom 'Update Method', Microsoft `List<T>.RemoveAt`, `RemoveAll`.
- 겹치는 표본: `object-pool-projectiles` (돌려주기 시점), `event-queue-sound` (모아 두었다 나중에 처리).

### E 생성 (새 그룹)

**`prototype-drone-clone` 프로토타입 패턴: 견본 드론 복제** ★★ — 묶음 2

- ID `prototype-drone-clone`, 그룹 E, 순서 1, 난이도 2.
- 한 줄: 다 설정한 견본 드론을 복제하되, 목록 같은 참조 필드는 새로 만들어 복제본끼리 섞이지 않게 한다.
- 수업에서 왜 필요한가: 교안 00 (값 형식과 참조 형식)과 Prototype (얕은 복사와 깊은 복사)을 한 화면에서 잇는다. 견본을 `MemberwiseClone` 만 하거나 `=` 로 대입하면 한 대에 단 모듈이 모든 드론과 견본에 생긴다. Unity 에서는 같은 일이 `ScriptableObject` 견본을 런타임에 고칠 때 일어나 Play 를 끈 뒤에도 에셋에 남는다. 교안이 "Instantiate 가 곧 프로토타입" 이라고 한 것도 글에서 잇는다.
- 무대와 시나리오: 도윤의 격납고. 견본 정찰 드론(HP, 속도, 장착 모듈 목록)이 왼쪽 받침대에, 복제본이 활주로에 줄 선다. 모듈은 드론 아래 작은 상자, 같은 목록을 가리키는 드론들은 같은 상자로 가는 `arrow` 로 그린다. 입력: `clone` 복제, `module` 마지막 복제본에 냉각 모듈 달기, `damage` 첫 복제본에 피해, `upgrade` 견본 개조 (속도 +). 자동 데모: 복제 셋 → 셋째에 모듈 → 첫째에 피해 → 하나 더 복제 (나쁜 예에서는 새 복제본이 이미 모듈을 달고 나온다). 시나리오 2: 견본 개조 뒤 복제 (이후 복제본만 빨라지고 이미 나간 것은 그대로 = 견본과 복제본이 독립). 조절 값: `maxClones`, `moduleSlots` 등 화면 차이가 나는 것.
- 효과 끄기: `Clone()` 이 `MemberwiseClone()` 만 하는 흔한 코드 (얕은 복사). HP 와 속도는 따로 복사되지만(값 형식) 모듈 목록은 모두 같은 목록이다. ✖ `모듈 공유` (한 대에 단 모듈이 다른 드론에도 보임), ✖ `견본 오염` (견본에도 생겨 다음 복제본이 달고 나옴). HP 는 정상이라 '값은 복사, 참조는 공유' 가 한 화면에 대비된다.
- `mistakes` 후보: `var copy = template;` 참조 대입, `ScriptableObject` 견본을 런타임에 고침, 장면에 있던 (이미 다친) 드론을 `Instantiate` 해 다친 채 복제, 깊은 복사 과잉 (공유해야 할 소유자·표적까지 복제), 같은 형식 인자가 많은 생성자에서 순서가 바뀜 (교안 Builder 를 한 줄로 녹임).
- 확인된 대표작: 없음 (범용 기법). 출처: 교안 `1. Creational/05. Prototype/`, `00. 객체와 메모리.md`, Nystrom 'Prototype' (https://gameprogrammingpatterns.com/prototype.html), Microsoft `Object.MemberwiseClone` 문서.
- 겹치는 표본: C# 문법 갤러리 후보 `value-vs-reference`. 묶음 3 `object-pool-projectiles` (재사용 때 초기화).

**`singleton-scene-managers` 싱글턴 패턴: 씬을 넘는 매니저** ★★ — 묶음 2

- ID `singleton-scene-managers`, 그룹 E, 순서 2, 난이도 2.
- 한 줄: 씬을 넘어 살아야 하는 매니저와 씬과 함께 사라질 매니저를 나누고, 둘 다 하나만 있게 한다.
- 수업에서 왜 필요한가: 교안이 다섯 형태로 가장 길게 다루고, 수업 프로젝트가 `SingletonBase` 를 이미 쓴다. 교안의 핵심 문장은 "유지해야 할 것과 씬과 함께 사라질 것을 구분" 이다. 증상: 기지로 돌아오면 BGM 이 두 겹이고 크레딧이 0 으로 보인다 (씬에 놓인 매니저가 또 생김). 씬이 바뀐 뒤 씬 종속 매니저를 불러 MissingReferenceException. 교안에서 비어 있는 '남용은 독' 절을 `mistakes` 가 채운다.
- 무대와 시나리오: 화면을 두 구역으로 나눈다. 정비 기지 씬과 지표 탐사 구역 씬, 지금 씬이 밝다. 매니저는 상자: `SoundManager` (유지, BGM 은 `ring`), `CreditBank` (유지, 크레딧), `ExpeditionManager` (탐사 구역 종속, 이번 탐사의 회로 조각 수). 입력: `toField` 탐사 구역으로, `toBase` 기지로, `pickup` 회로 조각 줍기, `settle` 기지에서 정산. 자동 데모: 기지 → 탐사 (조각 둘) → 기지 (정산) → 탐사 → 기지. 시나리오 2: 탐사 구역에서 정산 (지금 탐사가 있으면 정산되고, 기지에서는 받지 않음을 이벤트로 알림). 시나리오 3: 같은 씬을 연달아 다시 열기.
- 효과 끄기: `Awake` 에서 `Instance = this; DontDestroyOnLoad(gameObject);` 만 하는 흔한 코드 (중복 검사 없음), 씬 종속 매니저는 `OnDestroy` 에서 Instance 를 비우지 않는다. ✖ `중복 매니저` (기지로 돌아오면 SoundManager 둘에 BGM 두 겹, 새로 생긴 CreditBank 는 0), ✖ `파괴된 매니저 호출` (정산이 이미 파괴된 ExpeditionManager 를 부름. 예외는 관찰자 표본처럼 표시 필드로 흉내).
- 코어와 어댑터: 등록 규칙 `SingleSlot<T>` (먼저 온 것이 이긴다. 뒤에 온 것은 `false` 를 받아 스스로 파괴. 주인이 파괴될 때만 비운다. 교안 C 의 'case 1 권장') 과 크레딧·탐사 결과를 순수 C# 코어에 둔다. 씬 로드·언로드와 `Awake`/`OnDestroy` 순서는 Target.cs 와 sim.ts 가 흉내 낸다. Unity 어댑터는 `PersistentSingleton<T>`, `SceneSingleton<T>` 베이스와 매니저 셋.
- 위험: 코어가 얇고 대조의 상당 부분이 Unity 수명 흉내를 검사한다. 리뷰에서 흉내가 Unity 와 같은지 (같은 씬을 다시 열 때의 `Awake` 순서, `DontDestroyOnLoad` 오브젝트는 씬 언로드 때 남음) 따로 본다. 안 되면 묶음 3 의 `factory-drone-spawner` 와 자리를 바꾼다.
- `mistakes` 후보: 중복 검사 없음, 씬 종속 매니저를 `DontDestroyOnLoad` (지난 탐사의 수치가 다음 탐사에 남음), Enter Play Mode 에서 도메인 리로드를 끄면 static 이 지난 실행 값을 들고 있음, 아무 데서나 `Instance` 로 불러 의존이 숨음 (남용), 첫 접근 때 `AddComponent` 로 몰래 만들어 씬에 둘이 됨.
- 확인된 대표작: 없음 (범용 기법). 출처: 교안 `1. Creational/01. Singleton/`, Nystrom 'Singleton' (https://gameprogrammingpatterns.com/singleton.html), Unity 스크립트 레퍼런스 `Object.DontDestroyOnLoad`, Unity 매뉴얼 'Domain Reloading', Unity 전자책.
- 겹치는 표본: `observer-health-events` (파괴된 객체 호출을 흉내 내는 방식).

**`factory-drone-spawner` 팩토리 메서드: 드론 스포너** ★★ — 묶음 3

- ID `factory-drone-spawner`, 그룹 E, 순서 3, 난이도 2.
- 한 줄: 무엇을 만들지는 스포너 자식이, 만드는 절차(생성 → 배치 → 레이더 등록)는 부모가 한 곳에서 정한다.
- 수업에서 왜 필요한가: 교안 Factory Method 의 웨이브 스포너 상황이다. 교안 데모의 `Random.Range(0, 2)` 처럼 종류를 더해도 고르는 쪽 숫자를 안 고쳐 새 종류가 안 나오고, 종류마다 초기화를 복붙하다 한 곳에서 단계를 빠뜨린다. 교안 템플릿 메서드(적과 보스의 `Setup` 복붙)는 `Spawn` 이 절차, `CreateDrone` 이 훅이라는 것으로 녹인다.
- 무대와 시나리오: 정비 기지 앞 출구에서 정찰·중장갑·방패 드론이 나오고, 레이더가 살아 있는 드론 수를 센다. 포탑 일제 사격으로 드론을 줄여 웨이브가 끝나는지 본다. 자동 데모: 섞인 순서로 셋 → 일제 사격 둘 → 방패 드론 → 일제 사격 → 웨이브 끝 판정 (방패 HP 2 가 중장갑 HP 3 보다 낮아, 방패를 먼저 내면 방패가 먼저 파괴되어 거짓 웨이브 끝이 안 나온다. 워커가 순서를 바꿨다).
- 효과 끄기: 문자열 분기로 만들고 분기마다 초기화를 복붙한 흔한 코드. 섞인 순서가 종류 수를 숫자 2 로 박아 둬 ✖ `종류 누락` (방패 차례에 정찰이 나옴), 나중에 더한 방패 분기가 레이더 등록을 빠뜨려 ✖ `레이더 누락` (방패 드론이 남았는데 웨이브 끝).
- 출처: Refactoring Guru 'Factory Method', 'Template Method', Unity 전자책 (팩토리 장).
- 겹치는 표본: `prototype-drone-clone` (만드는 두 방법: 복제와 팩토리), `object-pool-projectiles`.

**`abstract-factory-zone-themes` 추상 팩토리: 구역 테마 세트** ★★ — 묶음 4

- ID `abstract-factory-zone-themes`, 그룹 E, 순서 4, 난이도 2.
- 한 줄: 구역마다 드론·투사체·바닥을 한 공장이 세트로 만들어, 다른 구역 것이 섞이지 않는다.
- 수업에서 왜 필요한가: 교안 Abstract Factory 의 웨이브 테마(숲/용암: 적·투사체·배경) 그대로다. 테마를 쓰는 곳마다 `switch (zone)` 을 두면 새 구역을 더할 때 한 곳을 빠뜨리고, 쏘는 순간 '지금 구역' 을 다시 읽으면 앞 구역에서 나온 적이 새 구역 투사체를 쏜다. 교안 예제 코드(`ForestDungeon.CreateProjectile` 이 `FireBall` 을 만든다)도 같은 실수를 한다 (분석 문서 5절).
- 무대와 시나리오: 숲·용암·빙하(나중에 더한 구역) 세 구역. 오른쪽 출구에서 구역 테마의 드론(덩굴·화염·서리)이 나오고, 각자 자기 세트의 투사체(가시·화염탄·얼음 조각)를 하린 쪽으로 쏜다. 자동 데모: 숲에서 하나 → 용암으로 옮겨 하나 → 사격 (남은 숲 드론) → 빙하로 옮겨 하나 → 사격.
- 효과 끄기: 쓰는 곳마다 `switch (zone)`. 사격이 지금 구역을 다시 읽어 ✖ `구역 섞임` (숲 드론이 화염탄), 빙하를 더할 때 투사체 switch 만 빠뜨려 `default` 로 ✖ `분기 누락` (서리 드론이 화염탄).
- 출처: Refactoring Guru 'Abstract Factory', Unity 매뉴얼 ScriptableObject.
- 겹치는 표본: `factory-drone-spawner` (팩토리 메서드는 제품 하나를 자식이 고르고, 추상 팩토리는 제품 세트를 공장 객체째 갈아 끼운다).

**`decorator-stat-buffs` 데코레이터 패턴: 버프 겹치기와 풀기** ★★ — 묶음 2

- ID `decorator-stat-buffs`, 그룹 F, 순서 1, 난이도 2.
- 한 줄: 기본 스탯은 그대로 두고, 버프는 감싸는 층으로 겹쳤다가 층을 빼면 원래 값이 된다.
- 수업에서 왜 필요한가: 교안 `A_StatBuff.cs` 상황이다. 버프 시작에 `attack += 5`, 끝에 `attack -= 5` 하는 코드는 배율 버프가 섞이거나 같은 버프를 다시 받으면 원래 값으로 돌아오지 않는다. "버프가 끝났는데 공격력이 그대로" 는 수강생 프로젝트에서 흔하다. 교안은 정석 감싸기(커피)와 목록 핸들러(스탯) 두 모양을 보이는데, 표본은 **활성 버프 목록에서 감싸기 사슬을 다시 만든다** 로 둘을 잇는다 (중간 층을 빼기 쉬움. 아래 결정).
- 무대와 시나리오: 하린과 '출력' 막대 (기본값 눈금을 `box` 로 표시), 버프마다 남은 시간 막대, 감싸기 사슬을 겹친 상자 (`[과부하 [냉각 셀 [기본 10]]]`)로 그린다. 입력: `cell` 냉각 셀 (출력 +5, 4초), `overload` 과부하 (출력 ×2, 3초), `purge` 정화 (모든 버프 해제). 자동 데모(6초 안팎): 냉각 셀 → 과부하 → 냉각 셀 다시 받음 (갱신) → 하나씩 끝남 → 모두 끝. 시나리오 2: 정화. 시나리오 3: 조절 값 (`cellBonus`, `overloadMultiplier`, 지속 시간)이 다른 경로.
- 효과 끄기: 시작 때 값을 직접 더하고 곱하며, 끝날 때 빼고 나누는 흔한 코드. 같은 버프를 다시 받으면 이전 타이머를 멈추고 새로 더한다 (`StopCoroutine` 으로 빼기를 건너뛰는 실수를 순수 C# 타이머로 흉내). ✖ `기본값 어긋남` (모든 버프가 끝났는데 출력이 기본값이 아님: 더하기 → 곱하기 → 빼기 → 나누기 순서가 섞여 10 이 12.5 가 되는 식), ✖ `중복 적용` (같은 버프를 두 번 더하고 한 번 뺌). 미니 월드에서 막대 끝이 기본값 눈금에서 벗어나 멈춘다.
- 결정 (되돌릴 수 있음): 층 순서는 '더하기 층이 안쪽, 곱하기 층이 바깥' 으로 고정하고 글에 적는다. 들어온 순서대로 감싸면 같은 버프 조합이 순서에 따라 다른 값이 되어 수업에서 헷갈린다.
- `mistakes` 후보: 코루틴을 멈춰 빼기를 건너뜀, 배율을 바로 곱해 두어 풀 때 나누기 오차, 최대 체력 버프가 끝날 때 현재 체력을 깎지 않아 상한을 넘음, 같은 종류 버프 갱신과 중첩을 구분하지 않음, 데코레이터 사슬 중간 층을 직접 떼려다 참조가 끊김.
- 확인된 대표작: 없음 (범용 기법). 출처: 교안 `2. Structural/04. Decorator/`, GoF 'Decorator'.
- 겹치는 표본: `prototype-drone-clone` (같은 '참조와 값' 주제), `observer-health-events` (출력이 바뀌면 알림).

**`facade-hit-resolution` 퍼사드 패턴: 명중 처리 창구** ★ — 묶음 3

**`composite-drone-squads` 컴포지트 패턴: 드론 편대 명령** ★★ — 묶음 4

**`adapter-sensor-units` 어댑터 패턴: 센서 장비 단위 맞추기** ★ — 묶음 4

- 한 줄: 장비마다 다른 API 와 단위를 어댑터 한 곳에서 우리 모양으로 바꿔, 화면과 경보는 한 모양만 안다.
- 수업에서 왜 필요한가: 교안 Adapter 의 결제·로그 어댑터(API 마다 절차와 매개변수가 다름)를 게임 안 장비로 옮겼다. 외부 SDK 를 쓰는 곳마다 직접 부르면 단위 변환을 곳곳에서 따로 하다 한 곳은 빠뜨리고 한 곳은 정수 나눗셈을 한다.
- 무대와 시나리오: 북쪽 A, 남쪽 B 두 구역의 방사선 센서. 실제 방사선은 같고 HUD 는 구역마다 막대(0~1)와 경보등. 도윤이 B 구역 장비를 외부 업체 신형(`ReadPercent()` 0~100 정수)으로 바꾼다. 자동 데모: 오름 → 교체 → 오름 (경보 수준).
- 효과 끄기: HUD 가 장비마다 직접 부른다. 막대 그리기는 변환을 빠뜨려 ✖ `막대 넘침`, 경보 판단은 `/ 100` 정수 나눗셈이라 ✖ `경보 누락`.
- 출처: Refactoring Guru 'Adapter', Microsoft Learn 산술 연산자 (정수 나눗셈).
- 겹치는 표본: `facade-hit-resolution` (퍼사드는 여럿을 단순한 창구로, 어댑터는 다른 모양 하나를 우리 모양으로), `decorator-stat-buffs`.

## 6. 근거가 약한 항목

- Unity 전자책의 수록 장: 싱글턴, 팩토리, 오브젝트 풀, 명령, 상태, 관찰자는 수록으로 알고 있으나 **전략 장 수록 여부는 미확인**이다. 카드를 명세로 옮길 때 전자책 목차를 확인하고, 없으면 `references` 에서 뺀다.
- Nystrom 웹판에는 데코레이터, 전략, 팩토리 메서드, 퍼사드 장이 없다 (프로토타입, 싱글턴, 오브젝트 풀, 이벤트 큐, 컴포넌트, 상태, 관찰자, 명령은 있다). 해당 표본은 GoF 를 이름으로 적고 교안을 함께 출처로 둔다.
- 카드의 URL 은 명세 작성 때 열어 확인한다 (지금은 기억에 기댄 것: Nystrom 장 주소, Unity `Object.DontDestroyOnLoad`, 'Domain Reloading' 매뉴얼, Microsoft `MemberwiseClone`).
- '수강생이 실제로 겪는 증상' 은 교안의 '상황' 코드와 Unity 커뮤니티에서 흔한 질문 유형에 기댄 판단이다. 수업에서 실제로 자주 본 증상을 Jay 가 알려 주면 시나리오 우선순위를 바꾼다.

## 7. 쟁점과 결정

| 쟁점 | 결정 |
|---|---|
| 웹 무대가 C# 를 직접 실행할 수 없다 | 코어를 TS 로 같은 이름으로 옮기고, 같은 시나리오를 dotnet 으로 돌린 기록과 줄마다 대조한다 (kit 설계 4-2절) |
| 나쁜 예를 C# 로도 둘지 | 둔다. 효과 끄기 화면의 버그가 C# 에서도 그대로 일어나는지 같은 방식으로 대조한다. 파일럿 비용을 보고 줄일 수 있다 |
| Unity 장면에서 실제로 돌려 볼지 | v1 은 컴파일과 dotnet 대조까지. 장면 연결은 `unity.setup` 글로 |
| 교안을 그대로 옮길지 | 옮기지 않는다 (Jay 확인). 강조점과 함정만 가져오고 상황은 외곽 탐사대, 글은 증상에서 시작 |
| 그룹을 교안 분류(생성·구조·행동)로 다시 짤지 | 다시 짜지 않는다. 기존 A~D (쓰임새 기준)는 두고 E 생성, F 조립을 더한다. 표본 `meta.group` 과 링크가 이미 A~C 를 쓴다 (되돌릴 수 있음: 그룹 키는 표본 id 처럼 영구가 아니라 meta 와 registry 만 고치면 된다) |
| 교안 명령 장의 Undo ('실행의 반대') 와 명령 표본 ('이전 상태 저장') 이 반대로 가르친다 | 표본은 그대로 둔다. 교안 쪽 보강을 Jay 에게 제안한다 (분석 문서 3절) |
| 싱글턴처럼 Unity 수명이 핵심인 패턴 | 등록 규칙만 코어에 두고 씬 수명은 Target/sim 이 흉내 낸다. 리뷰에서 흉내를 따로 검증한다. 안 되면 팩토리 표본과 자리를 바꾼다 |
| 데코레이터의 층 순서 | 더하기 층이 안쪽, 곱하기 층이 바깥 (고정). 명세에 적는다 |
